Context

A redBus-style bus booking marketplace, built from scratch. Four deliverables:

  1. Mobile app (Android + iOS, React Native): full bus booking features, high-quality graphics, animations, modern icons and fonts. Customers book only in the app.
  2. Marketing website (no booking).
  3. Operator portal: operators list buses directly, via their own ERP, or via a third-party ERP/software provider.
  4. Super admin panel: the client monitors traffic and manages buses, listings, operators and settings.

Third-party charges (payment gateway fees, SMS, push, maps) are separate and paid by the client at actuals.

Reality check: a full redBus clone is roughly 4–6 months for a team of about 6. Solo and part-time in 2 months needs a hard-cut MVP. ERP and third-party integrations are the largest risk, so launch with direct listing and add ERP adapters as an incremental phase.

How redBus-style platforms work

  • Three sides: operators (supply), customers (demand), platform (commission, typically 8–12%, plus convenience fees).
  • Customer flow: search, filters, seat map, boarding/dropping points, temporary seat hold (5–10 min), payment, e-ticket, cancel/refund.
  • Hardest part is inventory: no double-booking, so the seat hold must be atomic.

How one operator stays in sync across platforms

Take Laxmi Travels on redBus and AbhiBus. The operator has one central booking system (CRS/ERP, such as Bitla, Ticketsimply or eTravelSmart) holding the real seat inventory. Every channel (redBus, AbhiBus, counters, agents, us) reads and writes it via API:

  1. Search / availability (may be cached briefly)
  2. Seat layout
  3. Block seat: the real double-booking guard, always checked against the source of truth
  4. Confirm booking
  5. Cancel

There is no direct redBus-to-AbhiBus sync. Another model is quota/allotment: a fixed seat count per channel with no live sync. It is simple, but unsold seats get stranded.

Architecture AWS ap-south-1, t2.small to start

  • Monorepo (npm workspaces) on GitHub:
    • apps/api: Node.js + TypeScript + Express/Fastify + Mongoose, modular monolith, PM2 behind Nginx + SSL.
    • apps/web: React + Vite with separate areas for the marketing site, operator portal (/operator) and super admin (/admin); static build served by Nginx.
    • apps/mobile: React Native (Expo), Android + iOS.
    • packages/shared: TS types, zod validation, constants.
  • Deployment: EC2 in ap-south-1 (Mumbai), client-provided, starting on a t2.small (1 vCPU, 2 GB) and scaling as users grow. Nginx, PM2, SSL, Cloudflare (free) in front. Images on S3. Add 1–2 GB swap. A t2 throttles under sustained load (CPU credits); move to t3/t3a or larger when traffic grows.
  • Database: MongoDB (free hosted tier to start). No automatic backups on the free tier, so run nightly dumps to off-server storage and upgrade to a paid tier before real traffic.
  • No Redis, queue or Elasticsearch initially. Seat holds use MongoDB atomic operations; background jobs via node-cron in the API process.
  • UI/UX: modern design system (icon set, custom fonts, motion such as Reanimated/Lottie on mobile), designed in Figma before building each surface.

Core design decisions

  1. Seat inventory (own supply): one Trip doc per bus-departure-date with seats[{no, status, heldUntil, bookingId}]. A hold is an atomic findOneAndUpdate with $elemMatch on an available seat, so no transactions are needed. Holds expire in about 8 minutes (sweep job plus heldUntil check on read).
  2. Supplier adapter interface for every inventory source: search, getSeatLayout, blockSeat, book, cancel.
    • OwnInventoryAdapter: operators listing directly via the portal (built for launch).
    • ErpAdapter: one per ERP/CRS vendor, covering every operator on that vendor.
    • QuotaAdapter (optional): operator gives a fixed seat quota while selling elsewhere.
  3. Onboarding rule: do not list a bus as own inventory if the operator also sells it on another platform, unless they give a fixed quota. Otherwise the same seat is sold twice.
  4. ERP prerequisites: partner agreement with the operator or vendor, API credentials/sandbox, agreed commission and fare parity, and clarity on who handles refunds and complaints. The portal has a “connect ERP” flow storing credentials per operator, a sync status view and error alerts.
  5. Payments: Razorpay Standard Checkout. Server creates the order, the app pays, and an idempotent, signature-verified webhook confirms the booking. Reconciliation cron handles paid-but-unconfirmed and held-but-failed. Refunds via API; simple ledger with manual operator settlement at MVP.
  6. Auth: phone OTP (MSG91, DLT registration needed in India) plus JWT. Roles: customer, operator, admin.
  7. Search: MongoDB index on (fromCityId, toCityId, date) plus a cities collection for autocomplete.

Data model (MongoDB)

users, operators (KYC, commission %, listing mode: direct/ERP/quota, ERP credentials), cities, boardingPoints, buses (type, seat-layout template), routes, trips (bus + route + date + fare + seats[] + source), bookings (passengers, seats, status, pricing, supplier reference), payments, refunds, coupons, ledgerEntries, reviews, cmsPages, auditLogs.

Build order

  1. Backend and database foundation: everything depends on it (auth, data model, cities, buses, trips, seat hold, payments).
  2. Marketing website: quick, and a live site with policy pages is needed for payment gateway KYC and store review, so approvals can start while building.
  3. Operator portal: nothing is bookable until operators create buses and trips. Direct listing first; ERP and third-party adapters afterwards.
  4. Super admin (minimal first): approve operators, manage cities and routes. Dashboards, reports and settings follow.
  5. Mobile app: start as soon as search and booking APIs work, not only after admin is finished. Apple review (about a week) is the likeliest thing to overrun.
  6. Complete the admin (traffic monitoring, reports, refunds) alongside app testing.

Verification

  • seatHold tests: 50 parallel holds on one seat give exactly 1 success; expired holds are released.
  • Razorpay test mode: success, failure, abandon, duplicate webhook, webhook before redirect, paid after hold timeout (must auto-refund or re-confirm).
  • ERP adapter tests against vendor sandbox: block/confirm/cancel, timeouts, “seat taken elsewhere” handling.
  • E2E: search, hold, pay, ticket, cancel, refund on Android/iOS builds (Expo EAS), with operator and admin actions checked in the web portals.
  • k6 load test at about 50 concurrent users on the EC2 instance; watch memory (PM2) and database limits.
  • Backup/restore drill.
  • Pilot booking with a real operator before public launch.
